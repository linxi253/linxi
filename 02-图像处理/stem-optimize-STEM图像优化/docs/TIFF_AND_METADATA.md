# TIFF and metadata behavior

v2.1 accepts one homogeneous grayscale series. Every decoded page must be a
finite two-dimensional numeric array with identical shape and dtype.

OME outputs are generated by tifffile from the new stack shape, dtype, and
axes. PhysicalSizeX/Y/Z and TimeIncrement values and units are copied only
after parsing the input XML. Stale input OME-XML is never copied verbatim.

ImageJ metadata is restricted to documented scalar/list fields such as unit,
spacing, frame interval, labels, ranges, and info; numeric fields are validated
and invalid values are dropped. Generic TIFF retains XResolution, YResolution,
ResolutionUnit, and the input ImageDescription.

Classic TIFF is selected unless estimated uncompressed output approaches
3.7 GiB; larger output uses BigTIFF. Output is uncompressed for compatibility.
`imagecodecs` is installed so common compressed inputs can be decoded.

The sidecar is authoritative for processing provenance. It records both file
hashes, application and algorithm versions plus the numpy/scipy/opencv/
tifffile versions used, input/output structure, parameters, the CLAHE tile
grid, start time and processing duration, global percentile range, clipping
fractions, calibration, and completion status. It stores file names but omits
parent directories to reduce path disclosure.

Before publication, every output page is decoded again and checked for shape
and dtype. The validated TIFF is flushed to storage and then published with a
single atomic rename: a failed rename leaves the previous output untouched,
and the target path is never missing or truncated. The sidecar is published
next with the same atomic replace plus short retries; if it ultimately fails,
the previous sidecar stays unchanged and the completion message explicitly
reports that the new TIFF is published while its sidecar is stale. The output
directory is fsynced after publication where the platform supports it.
The input SHA-256 and filesystem identity are checked before and after
processing so a file changed in place cannot produce misleading provenance;
the export also verifies the signature captured when the file was opened, so
edits landing during confirmation dialogs abort the run.
