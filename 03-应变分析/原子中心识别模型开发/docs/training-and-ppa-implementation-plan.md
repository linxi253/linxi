# 原子中心识别模型开发与 PPA 接入实施规划

日期：2026-09-06  
状态：M1、M2、M3 已完成软件交付与合成验收；M4～M6 待实施。具体证据见 `reports/M123_DELIVERY_2026-09-06.md`（本地生成物，未入库）。  
依据：训练工具与 PPA 接入检查（`reports/TRAINING_PPA_READINESS_2026-09-06.md`，本地生成物，未入库）。

**目标：先完成不依赖真实训练集的软件建设，再用真实 HAADF-STEM 数据验收模型，最后发布可由 PPA 加载的模型包。HRTEM 沿用同一软件框架，单独建立数据、模型及验收标准。**

默认第一版面向本实验室的 HAADF-STEM 原子柱中心识别。精确适用材料、采样范围和应变噪声目标，在第一批数据审计时记录，在正式模型选择和盲测前冻结。

## 1. 实施原则与总体顺序

- **一个训练主项目。** “原子中心识别模型开发”承担数据组装、训练、评测和发布；PPA 消费模型和坐标。旧 atom_detector 只做必要修复、兼容或明确的迁移提示，避免两套训练流程持续分叉。
- **保持现有标签真值。** 原始 JSON 中的浮点中心点保留；对旧项目做可追溯迁移，YOLO 图像和框标签重新派生。旧记录补录的哈希只表示迁移时看到的文件，不能宣称验证了标注时的原始内容。
- **先验证正确性，再比较精度。** 合成数据可验证代码与模型计算流程；真实盲测负责判断科研适用性。
- **保护独立评测。** 划分在裁剪和增强前确定；模型选择只使用验证集；正式盲测保留至少两个完整独立采集批次。
- **分开部署依赖。** 训练使用现有 PyTorch/CUDA 环境；PPA 推理先使用已经可加载的 CPU ONNX Runtime。CPU 速度不足时再评估 GPU 推理环境。

实施依赖：

```text
M1 数值与配置修复 ─┐
                   ├→ M3 训练/推理/导出流程 → M4 PPA 开发联调 ─┐
M2 数据治理与组装 ─┘                                          ├→ M5 真实模型验收与发布
     └→ 真实图采集、试标、审核 ───────────────────────────────┘
                                                               └→ M6 HRTEM 扩展
```

M1 与 M2 的设计可以同期推进；M3、M4 可以用隔离的合成样本和开发模型完成。正式模型的放行依赖 M5。

| 里程碑 | 核心交付 | 是否需要真实训练集 | 完成的含义 |
|---|---|---|---|
| M1 修复配置、坐标、精修和评测 | 正确性修复及反例测试 | 否 | 已发现的代码问题可证明已修复 |
| M2 数据治理与组装 | 数据身份、分组审计、正式数据集生成器 | 开发不需要；正式数据审核需要 | 数据来源可回溯，重复和相关样本不会跨集合 |
| M3 训练、推理与导出 | 新训练入口、实际模型后端、ONNX 导出/验证 | 软件验收不需要 | 数据到位后可用同一流程启动训练 |
| M4 PPA 开发联调 | 后台检测、结果接收、状态与元数据保存 | 否 | 应用能够正确消费符合接口的检测结果 |
| M5 实验模型与正式发布 | HAADF-STEM 基线、盲测报告、发布包 | 是 | 模型在明确适用范围内达到预先约定的要求 |
| M6 HRTEM 扩展 | HRTEM 独立模型和验证报告 | 是 | 新模态通过独立验收 |

按交付条件推进，不把数据采集、标注或训练收敛承诺为固定日历工期。每次交付记录源码版本、配置和验证结果。

## 2. M1：先修复会影响运行和坐标可信度的问题

| 工作项 | 具体处理方式 | 验收标准 |
|---|---|---|
| 无效训练参数 | 移除直接传入 Ultralytics 的 brightness/contrast；配置加载采用公共配置 → 模态配置 → 命令行覆盖，并记录最终生效值；未知键启动即报错 | 正式训练配置通过本机库校验；修改配置确实改变实际参数；错误发生在启动训练或加载权重之前 |
| 灰度增强 | 亮度/对比度通过独立、受控的灰度变换实现；相关参数属于自有增强配置，不传入 YOLO 参数字典；验证/测试禁用随机增强 | 只作用训练图；中心点与几何变换保持一致；同一随机种子可复现；不会生成伪彩色通道差异 |
| 半像素坐标 | 保留已声明的像素中心约定，集中实现 YOLO 编解码和 ROI/缩放/填充逆变换；已有 Ultralytics Results 的原图坐标不能再重复撤销 letterbox | 整数点、亚像素点、非方形图、ROI 与切片边缘的往返误差符合数值/标签序列化精度；审计中的 +0.5 px 偏差消失 |
| 密集目标上限 | max_det 成为显式配置并写入模型 manifest；用训练集每切片目标数与适用范围设置余量；同步验证、推理和适用的导出设置 | 用超过 300 个、彼此可分的已知预测框验证不会被默认上限截断；达到配置上限时产生诊断信息 |
| 原始强度精修 | 管线保留原始强度与模型输入两条路径；在有上下文的原始图上精修，最后按 ROI 过滤；模型图归一化不能改变精修输入 | 同一原始图改变显示或模型归一化参数，不会改变固定候选点的精修结果；审计中的截断误差反例通过 |
| 精修失败与近邻 | 记录拟合状态、残差、位移量及回退原因；失败时保留原候选坐标并标记；按最短合理原子间距限制窗口、位移与合并距离 | 平坦区、边缘、暗峰、近邻、异常移动均有确定行为；失败不会把浮点候选悄悄取整，也不会静默删除疑似缺陷 |
| 旧评测入口 | main 使用已经存在的目录解析函数；保留空标签图；无匹配时误差标为不可定义，计数仍正常累计 | 对标准 YOLO 目录执行真实 CLI 可完成；背景误检计入 FP；零匹配不显示 RMSE=0 |
| 点匹配 | 实现“最大匹配数优先，其次最小距离”；用空间邻域和连通分量减少大图计算；如用惩罚成本，必须有保证最大基数的上界依据 | 审计中的 5 对反例返回 5；重复预测、多解、空集合和阈值边界有明确结果；代表性大点集运行时间/内存有记录 |

坐标合同固定为：

```text
原始点：全图 (x, y)，左上像素中心为 (0, 0)，数组索引 image[y, x]
ROI：半开整数边界 (x0, y0, x1, y1)
YOLO 边界坐标中心：local_xy + 0.5
网络输入坐标：scale * (local_xy + 0.5) + padding
从网络坐标恢复全图：((network_xy - padding) / scale) - 0.5 + crop_origin
```

上式用于确实返回网络输入坐标的后端；若框架已返回原图框坐标，则只执行尚未完成的变换。对边界框裁剪另定规则，原始点真值不能随框裁剪而改变。

数值验收应分层：纯浮点坐标变换验证机器精度级误差；8 位小数 YOLO 文本往返按图像尺寸计算允许的量化误差，常规尺寸可先用 1e-4 px 检查。它们是软件合同测试，不是模型精度指标。

## 3. M2：完成数据身份、迁移与正式数据集组装

**交付：可读取现有标注项目的数据审计器、迁移器和数据集生成器。**

1. 为原图记录文件 SHA-256、尺寸、数据类型、series/frame，以及采集批次和父视野标识。必要时增加未归一化图像平面的内容摘要，以发现重新封装为不同文件后的相同像素。
2. 统一 acquisition_id 的命名空间；将同一原图、同一父视野、连续帧/焦距序列、同一采集批次及其裁剪形成关联分组。完全相同像素不能证明所有相关视野都被发现，因此元数据仍是分组依据。
3. 自动发现跨任务重复，但不自动覆盖不同人的标注。重复图上的不同标签保留为标注版本，由负责人选定正式版本或完成仲裁后再导出。
4. 旧任务保持可打开。新增字段按版本迁移，生成新项目/清单和迁移记录；原标签保留。缺少真实批次信息时允许继续草稿标注，正式划分前应解决来源不明或关联不清的分组。
5. 从已审核且完整覆盖的 ROI 生成数据集；保留已确认无原子的背景 ROI。未审核区域不能充当负样本。
6. 先在源数据层冻结 train/val/test，再派生裁剪和增强。正式盲测至少两个独立批次；比例不足时优先保证隔离和独立批次数，并报告实际比例。
7. 冻结原始点真值和导出参数；内容更新产生新版本。测试集被用于失败分析并影响模型后，它只能作为开发证据，下一次正式结论需要新的独立盲测数据。

正式派生产物应包含 data.yaml、各集合图像与标签、原始点真值、source_map、数据摘要与审计报告。所有路径可在迁移目录后解析，原图、帧、ROI、派生点和 split 可相互追溯。

**验收：**

- 审计报告中的同图跨四任务例子，被识别并放入同一个隔离分组；不存在跨集合内容或来源关联泄漏。
- 同路径原图被替换时阻止继续静默使用旧标签，并显示需要处理的记录。
- 空背景保留，未审核内容排除；已有 JSON 点位不因迁移或导出改变。
- 重复标注冲突、缺失来源和正式盲测批次数不足均产生具体诊断。
- 相同源数据、配置和种子生成相同分组和内容摘要；时间戳不进入影响数据身份的内容摘要。

## 4. M3：在新仓库打通训练、实际推理和 ONNX 导出

**交付：一套可执行命令，完成数据检查 → 训练 → 评测 → 导出 → 部署验证。命令名称在实现时确定。**

训练部分：

- 统一配置读取；启动前检查模态、数据审计、输入尺寸和 GPU 可用性。
- 先用小型 YOLOv8 网络完成软件冒烟，再以 YOLOv8s 作为第一版候选基线。640 输入沿用已测试路线；batch 根据目标密度和峰值显存确定，记录实际值。
- 每次运行使用独立目录，记录数据摘要、完整参数、代码版本、随机种子、依赖版本、初始化权重来源/哈希，以及 best/last checkpoint。
- 断点续训显式指向原运行；更换数据集或配置后不能无提示地“续训”。不同模态和不同实验不能覆盖同一个 best.pt。
- 建立纯推理可安装的依赖组合；PPA 端导入推理模块不得强制导入 torch、ultralytics 或标注 GUI。
- 同步包版本和依赖快照，并在干净环境验证按锁定规则安装。

推理与导出部分：

- 实现实际 PyTorch 候选后端和 ONNX Runtime 候选后端，统一输出 CandidateSet。
- 固定输入通道、NCHW、dtype、归一化、填充、输入尺寸及输出张量语义；首版采用静态尺寸 FP32 ONNX，opset 以现有 Runtime 的实际兼容性测试为准。
- 优先导出无内置 NMS 的 ONNX，让两种后端复用解码、坐标恢复和后处理；显式执行目标数量上限。
- 模型输入的归一化作用范围必须与训练数据导出一致，并被记录；不能训练时按 ROI 归一化、部署时无说明地按全图归一化。
- 执行真实网络的 PyTorch/ONNX 张量和点输出对照，覆盖空图、密集目标、弱信号、ROI、非方形图及切片重叠。

**无需真实数据的验收：**

- 在隔离的合成开发数据上，用正式训练入口完成短训练、保存、恢复、导出及 ONNX 实际加载。
- 后端从图像自行预测，不再以已知真值直接作为候选点；已知候选测试继续用于独立验证几何和精修。
- 实际网络的 ONNX 数值误差、置信度差和匹配点差有报告。阈值附近的输出单独诊断；远离阈值的样例应有一致检测数，FP32 点差可先按 0.01 px 作为软件验收候选线并验证合理性。
- 每个错误返回明确非零退出码，指向配置、数据或模型问题。
- 合成开发模型写入开发运行目录，标明用途，不进入正式发布目录。

## 5. M4：PPA 开发联调

**交付：可选模型检测入口、推理适配器、结果提交与项目保存支持。**

- PPA 通过统一 provider 获取 DetectionResult；采用 package/wheel 依赖或明确的运行时打包方式，不依赖开发电脑临时添加的绝对源码路径。
- 从原始图和显式帧发起检测，后台运行；取消、切换图像、切换帧或修改任务状态后，旧结果不能覆盖当前点表。
- 结果在 Tk 主线程提交。复用追加/替换点的现有流程，同步 point_size、清理选中/参考选点状态并使过期分析结果失效。
- 模型置信度和拟合质量使用独立字段，不能塞入 point_size；保存、追加、删除、撤销与重排时保持逐点对应。手工点的模型置信度应标为不适用。
- 将图像身份、帧、模型/配置摘要、模态与点来源写入项目。修改点位后清理受影响的分析数据；不自动把低置信度或疑似缺陷点删掉。
- GUI 点始终 y 向下；进入应变核心时由现有 PPA 代码转换到物理 y 向上，避免重复翻转。
- 运行时缺失、模型校验失败或无可用模型时，传统检测功能仍可正常使用；错误提示说明具体原因。
- 保留人工确认、参考晶格和参考区选择步骤。开发联调用受控测试 provider/开发模型；正式模型入口的发布要求由 M5 决定。

**验收：**

- 现有 PPA 数值与 GUI 测试继续通过。
- 追加、替换、手工编辑、保存重开、ROI、多帧、取消和过期结果等工作流保持数据对应关系。
- 已知拉伸、剪切、刚体旋转与零应变合成例子恢复预期结果；相同点表经传统入口或模型入口提交时，应变结果一致。
- 在不安装 PyTorch/Ultralytics 的推理环境验证应用启动、ONNX 检测与项目保存。
- Windows 源码运行和打包运行都能定位 Runtime、模型文件及配置；修复并验证已发现的窗口退出回调清理告警。

## 6. M5：真实 HAADF-STEM 基线、盲测与发布

这一阶段需要实验数据。软件建设期间可以同步完成采集信息整理和试标；正式标注工具版本由 M2 的兼容性验收决定。

数据推进采用两轮：

- **流程试标：** 参考已有采集指南，先整理约 10–15 个独立视野、至少 3 个真实采集批次；先共同标 3–5 张统一规则。这批数据用于检查流程和暴露问题，不作为最终精度证明。
- **真实基线：** 在试标基础上覆盖预定材料、像素尺度、弱峰、密集近邻、背景、界面和缺陷。数据规模沿用现有阶段指南作为起点；正式盲测至少留出两个独立批次。是否足够由学习曲线和各场景结果判断。

在模型选择前定义并冻结以下内容：

| 项目 | 需要预先明确的内容 |
|---|---|
| 适用范围 | 材料/晶带轴、显微模式、像素尺寸、极性、目标原子间距和图像质量范围 |
| 标注可信度 | 第二人复核与标注者间差异；不确定区域规则；原子柱中心语义 |
| 定位要求 | 匹配阈值、precision/recall/F1、x/y 系统偏差、RMSE 与 95 分位；有标定时换算 pm |
| 下游要求 | 已知无应变参考区的应变均值偏置与标准差；已知变形恢复误差；边缘/缺陷的有效位点和质量规则 |
| 使用要求 | 代表图尺寸和原子数下的响应时间、内存、人工修改工作量，以及失败提示 |

在训练/验证批次上比较传统检测、网络框中心、网络加 COM、网络加高斯精修。报告整体与困难场景结果；只在匹配点上得到的低 RMSE，不能掩盖大量漏检。置信区间按独立批次或视野评估，不能把同一图上的大量原子当作相互独立的实验样本。

模型、阈值、精修和质量规则冻结后，再运行正式盲测。若结果未达到事先定义的使用要求，返回训练数据和适用范围分析；不通过反复调试同一盲测集获得“达标”结论。

正式发布包必须包含：

- ONNX 模型、完整 model_manifest、SHA-256 与固定输入/后处理/精修配置。
- 训练数据版本、来源摘要、模型初始化信息、软件版本和对应源码版本。
- 真正原子模型的 ONNX 一致性报告、真实盲测报告、适用范围和限制。
- PPA 在目标 Windows 推理环境中的验证记录。

发布准入增加必填字段与“实验验收通过”条件；文件哈希匹配只证明内容一致。PPA 沿用已登记模型的信任边界，不把任意目录里同时出现的模型和自填 manifest 自动视为正式发布。

**验收：完整发布包通过校验，PPA 实际加载该模型，在冻结的独立实验集及目标机器上满足预定要求。** 模型可以作为候选点辅助工具使用到什么程度，由真实评测决定，不能自动等同于科研应变精度已达标。

## 7. M6：HRTEM 扩展

- 复用已验证的软件链路，使用独立的 HRTEM 数据清单、模型和发布目录。
- 对离焦、厚度、明暗/混合对比和像差条件制定标签规则；无法可靠判断的区域不猜测标注，必要时增加成像模拟或可靠参考支持。
- 专门验证 auto 极性和 COM/高斯精修是否仍符合“投影原子柱中心”目标，不能直接继承 HAADF-STEM 的参数或结论。
- 独立进行批次隔离、定位与 PPA 下游验收。
