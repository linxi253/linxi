## F01 · P1：整数索引取整破坏局部邻居拓扑

位置：[ppa.py:577](H:/AIforTEM/03-应变分析/原子级应力分析-PPA/ppa.py:577)、[ppa_core/strain.py:312](H:/AIforTEM/03-应变分析/原子级应力分析-PPA/ppa_core/strain.py:312)。证据：`probe_alias`。

`assign_unique_lattice_indices` 先把每个变形点投影到全局参考基矢并独立取整。局部 PPA 随后直接以整数索引的 ±1 判断邻居。唯一索引只能避免重复编号，不能保证这些整数索引保持真实的原子邻接关系。即使没有索引冲突，累计位移跨过半个晶格步也会产生索引跳变，改变用于求导的参考邻域。

本次使用 12×100、间距 10 px 的完美晶格，施加 `F=[[1,0.02],[0,1]]` 和 0.1 px 平移：

- 张量剪应变解析值为 **0.01**。
- 初始取整冲突数为 **0**。
- 当前链路有 **48/1200** 个错误位点，结果范围为 **[-0.294738, 0.010000]**。
- 其中 **40 个**仍标为 `A-symmetric`。
- 用真实索引和原始参考位置直接调用相同核心函数，最大误差只有 **5.19×10⁻¹⁶**。

这定位了故障源：参考位置和邻居索引被改写，公式本身并没有造成上述误差。测试中也确实有 **121 个低置信度匹配标记**，因此不能说程序完全没有质量提示；问题是提示没有阻止错误邻域被作为有效应变输出，且逐原子应变 CSV/统计链路不能据其 A/B/C 标签识别这种拓扑错误。

建议以几何方向、局部步长、互易配对和闭环一致性验证邻居拓扑，再求 F。全局晶格索引用于解释和追踪，不能独自承担科学有效性判据。无法确定拓扑时保留原子和位移，应变标为 NaN 并说明原因。不能用全图仿射精化或线性去趋势来“修复”这个反例，这会吸收真实均匀应变。

验收：扩大晶格尺寸、改变原点、加入小剪切/旋转/拉伸/空位，对照解析结果；必须覆盖累计位移超过半格的情形。错误拓扑不得仍得到有效 A 级应变。

## F02 · P1：非保向或退化映射仍返回正常质量等级

位置：[ppa_core/strain.py:127](H:/AIforTEM/03-应变分析/原子级应力分析-PPA/ppa_core/strain.py:127)、[ppa_core/strain.py:142](H:/AIforTEM/03-应变分析/原子级应力分析-PPA/ppa_core/strain.py:142)、[ppa_core/strain.py:239](H:/AIforTEM/03-应变分析/原子级应力分析-PPA/ppa_core/strain.py:239)。证据：`probe_nonphysical_F`。

核心只验证参考邻域，不验证变形梯度的行列式和退化程度。`_polar_angle` 还在检测到反射时强行把 SVD 的旋转行列式改成 +1，没有向调用者暴露非物理映射。

解析反例 `F=diag(-1,1)` 和 `F=diag(0,1)` 在局部 PPA 的 25 个位点以及 CST 的 32 个三角形上均得到 `quality=True`。反射的 GL 等效应变为零或机器精度零。这符合 `FᵀF=I` 的代数结果，却不能证明它是合法的材料变形；塌缩映射的旋转也没有唯一、可靠的物理解释。

误检、错配和翻折三角形可在真实数据中触发该问题。应在公共结果入口检查 F 的有限性、`det(F)>tol` 和最小奇异值；失败行保留、应变/旋转设 NaN，并提供 `orientation_reversed` / `collapsed_map` 等原因。CST 也应保留可追踪的质量信息，避免异常元素参与统计。不能按应变幅值大小删除真实缺陷信号。

验收：两种算法都覆盖反射、塌缩、接近奇异、合法大旋转和合法拉伸；非物理映射不得标为有效。

位置：[ppa.py:3528](H:/AIforTEM/03-应变分析/原子级应力分析-PPA/ppa.py:3528)、[ppa.py:5712](H:/AIforTEM/03-应变分析/原子级应力分析-PPA/ppa.py:5712)。证据：`probe_close_callback` 和现有测试日志。

## 性能与资源边界

本次没有在当前机器上测得应当描述为“数千点必然卡死”的现象，不能沿用旧性能报告的数字。单次真实晶格匹配、仅一个冲突：2500 点约 **0.020 s**，10000 点约 **0.124 s**；仅代表本机这两种合成输入。该步骤仍在 Tk 主线程，更多冲突、参考区多次拟合与大输入应单独测量。

优先治理下列资源路径：

| 路径 | 当前问题 | 建议 |
|---|---|---|
| TIFF 读取 | `tifffile.imread` 先解码整个堆栈才要求选帧；图像/JSON 缺少规模上限 | 先检查元信息，再读取选定帧；给受支持尺寸和像素数建立约束 |
| 批量 COM | 生成 `(N,window,window)` 拷贝及多个同规模临时数组 | 分块处理；限制窗口；10000 原子、101 窗口，**单个 float64 数组已约 778 MiB**，本次只算资源量，没有实际分配 |
| NMS | `query_pairs` 一次枚举全部近邻对，密集候选或极大半径可达 O(N²) 边数 | 按已接受点查询邻居，避免先存完整图；限制参数并监测候选数 |
| 应变插值 | 对 9 个分量反复三角化/估计几何 | 对相同有效掩码缓存三角化，使用多列值批量求值；不同掩码不能混用 |
| 取消检测 | 代际主要阻止提交，不会打断逐峰高斯精修 | 在分块/逐峰边界检查取消，使用有界任务执行器，避免连续启动留下多个耗时 worker |
| 预处理、哈希、统计导出 | 多个重任务仍在 Tk 主线程 | 把纯计算与 IO 移到后台，主线程只处理状态、对话框和结果提交 |
| 位点极分解 | 逐矩阵 Python 循环调用 SVD | 评估批量 SVD；先确保 F02 的有效性处理，再优化 |

实现时保持取消、点表修改后的任务失效以及关闭处理的正确性，不能把它们当作无用状态删除。

## 安全与权限审查

当前架构是本地单用户桌面工具，没有发现 HTTP 服务、远端对象 API、多租户资源或登录会话。权限边界主要是 Windows 文件权限、可执行扩展及模型信任，而不是为桌面程序补一套 JWT/RBAC。

| 边界 | 当前判断 | 应处理的实际问题 |
|---|---|---|
| 项目 JSON | 使用 JSON 解析，没有发现项目字段经 eval/exec 执行 | F05/F06/F07：身份绑定、完整 schema 和事务加载 |
| YAML | 可选推理配置使用 `yaml.safe_load` | 仍需字段类型、范围和资源约束；safe_load 不是业务 schema 校验 |
| OS 文件权限 | 主 GUI 多数写入已捕获 OSError，未发现提升权限动作 | F08：失败必须准确反馈；统计批量导出还需统一处理部分完成与 IO 错误 |
| 可选 `.pt` | 稳定 GUI 不加载；可选检测器在 YOLO 前调用 SHA-256 白名单检查 | 保留该边界。白名单是明确登记的信任，不是模型来源认证 |
| 可选模型的路径校验与加载 | 校验后再按路径交给 YOLO，仍存在文件版本变化窗口 | 对需要抵御可写模型目录中替换行为的场景，使用经核实的不可变快照。此项为条件风险，本次没有真实模型攻击验证 |
| 白名单写入 | 记录来源与时间，CLI 有明确登记流程 | 建议摘要标准化、API 参数校验和原子更新；文件 ACL 应与受信模型目录的权限模型一致 |
| `butter.py` 扩展 | 从显式环境变量/工作区代码目录导入，临时 sys.path 会恢复 | 将目录作为可信代码边界；可选扩展的非 ImportError 异常仍可使主模块导入失败，应与可用性策略一致 |
| 依赖与发布物 | 运行锁版本可核实；可选 ML 依赖没有同等锁定 | 本次未做独立 CVE 数据库扫描、供应链认证或 EXE 签名验证，不把 `pip check` 解释为这些验证 |

没有发现稳定 GUI 绕过模型白名单加载任意 `.pt` 的证据。不能把用户可编辑的路径/白名单本身泛化为远端越权漏洞，也不能把 SHA-256 当作对恶意来源的认证。

## 内部结构与可维护性

`ppa.py` 有 5715 行、AtomMarkerApp 有 121 个方法；`ppa_stats.py` 有 1661 行、PPAStatsApp 有 28 个方法。**大文件本身不构成缺陷**。真正的问题是多份状态真源和缺少统一提交边界，已经在 F03/F04/F06/F13/F16 中形成可复现错误。

| 责任 | 当前情况 | 优先改善 |
|---|---|---|
| 科学计算 | F、应变与旋转已放入 ppa_core；参考格/索引和一部分纯辅助仍在 GUI 模块 | 用可导航的纯函数边界明确输入/输出，不按行数机械拆分 GUI |
| 分析请求与结果 | 数值参数已部分快照；结果分散在几十个可写实例字段 | 明确 AnalysisRequest / AnalysisResult / Provenance，整体提交，保留原 API 入口 |
| 状态失效 | `_clear_analysis_results` 与 `reset_all` 各自维护一份清理字段 | 建立唯一失效入口和清晰状态转换；避免复制清理列表 |
| 项目格式 | core 检查版本/图像，GUI 检查部分字段 | core 统一解析与校验 ProjectData；GUI 负责用户决策与提交 |
| 点表操作 | 编辑函数和检测合并分别修改列表，撤销靠数组索引 | 点表命令统一管理增删/替换/追加与失效，必要时引入稳定原子 ID |
| 统计输入 | 不同 CSV 独立加载到同一共享容器，来源只保留一个 algorithm_id | 分析批次持有独立输入、质量筛选和统计口径，杜绝隐式混合 |
| 渲染 | 已有物理/显示符号转换函数，但两 GUI 的插值范围和统计图逻辑仍分叉 | 共用坐标/网格定义和图表计算数据，再分别渲染 |
| 错误处理 | 后台队列已有异常隔离；其余保存/加载路径的成功条件不统一 | 明确“完整成功、部分完成、失败、取消”状态，向上返回结构化错误 |
| 导入副作用 | GUI 导入改变 stdout 编码、Matplotlib 后端和全局字体，加载扩展 | 避免纯数值消费者必须导入 GUI；在嵌入 Suite 场景验证全局后端/样式兼容 |
| 测试 | 测试已覆盖许多历史问题，但不足以检验完整科学/状态契约 | 添加跨视场解析场、失败无副作用、控件变化溯源、重置与关闭的场景测试 |

推荐状态流是“输入版本 → 请求快照 → 后台计算 → 校验版本 → 整体结果提交 → 按结果来源导出”。参考区、图像、点表与算法参数必须明确属于哪个版本；结果不是若干散落数组的隐式组合。
